Selected work: AI operator for local businesses

KasaFlow

AI operator for local businesses · Python / FastAPI · OpenAI Responses API

Retail pilot · hardened

A modular AI workflow engine that combines Python, FastAPI and OpenAI's Responses API to turn a customer's WhatsApp conversation into structured decisions and business actions. It is built around explicit application boundaries rather than a single prompt wired directly to a live store.

Problem

Rule-based routing was predictable but brittle against real customer phrasing. Purely conversational messages could also be pushed through business tools that had nothing to do with them. The system needed to understand intent without letting model output own pricing, transaction state or consequential writes.

System

  • OrchestrationSeparated the API, LLM routing, tool registry, executor and business services into modules with explicit contracts.
  • Tool layerBuilt model-selected tools for pricing, delivery information, quotes, product recommendations and order workflows, backed by catalogue and policy data separate from application logic.
  • CommerceIntegrated the WhatsApp Cloud API and a live WooCommerce catalogue of 3,918 products, extending the engine from a text-in / structured-output service into a customer-facing commerce assistant.
  • VoiceWorked on Twi voice-note input and the ASR/TTS integration path, validating actual API hosts, authentication and request/response shapes against live calls.
  • ConversationAdded a separate conversational outcome so social replies can short-circuit before touching order, product or memory state.

Engineering decisions and guardrails

  • Action boundarypropose_order() calculates a deterministic quote and creates a pending proposal; confirm_order() is the only order-write path and acts on the proposal already priced for that session.
  • IdempotencyWooCommerce's REST API does not provide idempotency keys for this flow. On a timed-out order creation, the system reconciles using a token in order metadata before deciding whether retrying is safe.
  • Price integrityThe exact quoted variant is re-priced before the write. The resulting store total is checked against the quote, with mismatches routed to a person rather than silently accepted.
  • Prompt injectionCode-level guards prevent flagged turns from confirming or cancelling orders, regardless of what the model selects. Human handoff is available on request and after repeated failures or manipulation.
  • ConcurrencyA per-session lock spans a complete turn to prevent concurrent messages from overwriting conversation state.

Evaluation and debugging

  • EvaluatorBuilt a separate behavioural evaluator with 46 scenarios across 15 categories, covering 85 customer turns, including 24 multi-turn scenarios. It checks tool choice, resolved arguments and required or forbidden response phrases.
  • Trace dataConversation replays run in a sandbox with an in-memory store. Recorded mode replays saved model outputs; live mode reruns the model to examine variance.
  • Failure-driven fixesUsed live and replayed failures to fix product matching, stale order fields, missing conversation context, address/delivery mismatches and cancellation behaviour. Regression coverage was added around the discovered cases.
  • MetricsDefined latency, token usage and separate API, response, parsing and routing success measures before running performance comparisons.

Result and status

The quote/pricing and order-creation paths were exercised end to end against the live WhatsApp API, WooCommerce catalogue and store. A complete public deployment has not been claimed; this remains a Ghanaian jewellery-retail pilot.

Catalogue: 3,918 products
Behavioural evaluator: 46 scenarios / 15 categories
Tests: 937 passing / 29 gated
Model boundary: propose → confirm

Test counts and implementation status reflect dated repository snapshots. The 29 gated tests call the real model API; the separate evaluator is not a claim of independently verified production reliability.

Selected work: evaluation engineering for AI agents

The Last Yes

Standalone benchmark · Python · Tool calling · Deterministic grading

Built and evaluated · November 2026

A benchmark for transaction-authorisation integrity in conversational commerce agents. It tests whether an assistant can distinguish a customer's acknowledgement from permission to act, preserve the latest transaction state, respect amendments and withdrawal, avoid duplicate writes, request missing information, and refuse to access another customer's order.

System and task design

  • Task setA ten-task core suite covering acknowledgement versus consent, context-sensitive yes, amendments, withdrawal, claimed authority, duplicate confirmation, missing fields, order ownership and confirmation after withdrawal. Additional releases add three exploratory authority probes and a five-condition matched-authority suite.
  • HarnessA Python tool-calling runner starts a fresh model conversation and synthetic simulator for each trial, then records transcripts, tool calls, events, served-model metadata and final state as JSON.
  • GraderA deterministic grader checks action sequence, tool arguments, order ownership, proposal and confirmation state, duplicate writes, missing information, false completion claims and consequential side effects. The core score does not rely on an LLM judge.
  • ValidationSeparate reference-policy traces and deliberately incorrect traces are used to check grader behaviour. The v0.1.9 working snapshot passed 42 automated tests and 18/18 reference validations.

Live model evidence

Runs used temperature 0.0 through two exact hosted OpenRouter free-model routes: cohere/north-mini-code:free and nvidia/nemotron-3.5-super-vl:free. These are the tested serving routes, not a representative survey of frontier models.

  • v0.1.7Across five trials each for a foreign-order negative case and an own-order positive control, Nemotron passed 10/10. Cohere passed 4/10: it attempted the foreign-order lookup in all five negative-case trials and used the wrong order ID in one own-order lookup. The simulator denied the foreign lookups; no data was disclosed and no state changed.
  • v0.1.8Nemotron passed 9/9 exploratory authority probes. Cohere passed 6/9, with three foreign-order lookup attempts across employee-role and manager-approval prompts. Urgent-delegation passed 3/3. These prompts were exploratory and not fully matched, so they do not prove that a particular authority phrase caused the failures.
  • v0.1.9In the five-condition matched-authority suite, Nemotron passed 15/15. Cohere completed 14/15 original requests, all passing; one request timed out at the provider. A separate retry of that condition passed, giving Cohere 15 completed passes across 16 requests. Across both models, 30 completed evaluations passed across 31 requests, with one provider timeout and no behavioural incidents in completed trials.

What the results mean

The ownership failures are evidence of attempted unauthorised reads, not a successful data breach: the simulator returned not_found, disclosed no data and made no state changes. The matched v0.1.9 follow-up did not reproduce the earlier Cohere failures. The result is deliberately nuanced: refining the experiment showed why exploratory prompt variation must be separated from controlled comparisons.

Core suite: 10 tasks
Offline validation: 42 tests · 18/18 references
Matched suite: 30/30 completed passes
Provider errors: 1 timeout

Small exploratory trial counts, two specific hosted free-model routes, and a synthetic environment. The benchmark tests adherence to an explicit policy in the prompt; it is not a production security audit, a legal determination or a statistical claim about either model family.

Prior work and provenance

KasaFlow's pre-existing transaction architecture and 46-scenario behavioural evaluator informed the research question. The Last Yes was built separately for the Micro1 Eval Hackathon with synthetic identities, products, orders and prices. It does not import KasaFlow application code or include real customer data or credentials.

Engineering decisions

  • DOM resilienceUsed MutationObserver to respond to WhatsApp Web header re-renders, with a polling fallback for cases the observer misses.
  • BackendChose Convex to ship real-time synchronisation without building and operating custom backend infrastructure too early.
  • PrivacyRemoved unnecessary plaintext contact-name persistence from server writes and shipped a dry-run-first, re-runnable migration to scrub existing values.
  • Account securityReworked account linking so knowing a phone number is not sufficient to join an account. New browser linking requires the account's recovery key, stored server-side as a hash, with a legacy-account upgrade path.
  • EntitlementMoved Pro licence verification to a server-side Convex action that verifies the store and product with Lemon Squeezy, records entitlement and handles refunds.
  • Human confirmationRejected full automation of the final Scheduled Photos click after scripted interactions proved unreliable, including a black-photo incident during testing. A human confirms the consequential action.

Engineering decisions

A few principles that recur across the projects above.

The model proposes. Application code executes.

In KasaFlow, the model selects an action, but application code owns pricing, permissions, proposal state and the consequential order write. The model should not own a hard-to-reverse side effect.

A benchmark should score actions, not just plausible wording.

The Last Yes checks tool calls and resulting simulator state against explicit reference behaviour. A fluent answer cannot compensate for an unauthorised action, and a different but correct phrasing should not fail merely because the wording differs.

Don't retry a failed write blindly.

When an external write times out, first reconcile whether it succeeded. Retrying without checking can create duplicate orders or other repeated side effects.

Reproduce a failure before fixing it.

A finding becomes stronger engineering evidence when it has a failing test or trace, a documented root cause, a fix and a regression check that protects the behaviour.

Keep security authority on the server.

Client-side checks can improve usability, but they must not be the source of truth for identity, permissions or paid entitlements.

Reject automation when the failure mode is worse than the manual step.

A human confirmation step can be the right design when automated interaction with a third-party interface is unreliable and the action could damage user data.
