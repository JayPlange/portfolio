01

Case study: shipped & owned end to end

DualProfile

Chrome extension SaaS · vivaup.org · Manifest V3 + Convex

Live, paying users

WhatsApp Web renders one profile photo to everyone in your contact list. DualProfile lets a user assign a different photo per contact, visible only to that person, with mutual detection running on hashed phone-number lookup between two installs.

  • ProblemI don't control WhatsApp Web's DOM, and it changes under me without warning.
  • DecisionMutationObserver over polling to catch header re-renders live, with a polling fallback for anything the observer misses, so overlay rendering degrades gracefully instead of breaking outright.
  • IncidentA device-auth migration silently forked live accounts: registering a device before its phone number was known created a second Convex user sharing that phone hash, orphaning existing photos and assignments. Root-caused by diffing server truth against client state across two live installs, repaired in place with a dry-run-first migration — then patched again when the same gap resurfaced through a second code path.
  • Scheduled PhotosA second delivery mechanism, built after per-contact overlays alone couldn't answer "I want everyone to see my new photo": switches the account's real WhatsApp photo by day/time, visible everywhere, mobile included, no counterparty needs anything installed. Scripted clicks on the final confirm step proved unreliable under real testing, including one black-photo incident before the fix, so I deliberately rejected full automation. A human taps the last confirm, every time — the one action that reaches WhatsApp's own servers; everything else in DualProfile is a pure browser-side overlay that never touches them.
  • Trade-offConvex over custom backend infra: accepted vendor lock-in to ship real-time sync solo, instead of over-engineering for scale I didn't have yet.
  • MonetisationCollapsed a four-tier Free/Pro/Annual/Lifetime structure down to Free/Pro after data showed the middle tiers weren't converting. Limits are still enforced inside the same Convex mutation that writes the assignment, not the client, so entitlement can't be bypassed by editing the extension.
  • RepricingCut the single Pro tier from £29 to £9.99, reusing the existing Lemon Squeezy variant rather than creating a new one so the checkout URL, webhook mapping, and existing customers' entitlement stayed untouched. The reprice surfaced a real bug in the process: the extension's own paywall modal had £29 hardcoded in JavaScript rather than read from config, so the live purchase flow and the landing page were quoting two different prices before this was caught and fixed.
  • PrivacyFound the server held a de facto phone-number-to-contact-name map: contactName was written in plaintext alongside a phone-hash that's reversible by exhaustive search, contradicting the product's own privacy claim. Stopped writing it at every call site, made the schema field optional rather than deleting it outright so existing rows still pass validation, and shipped a dry-run-first, re-runnable migration to scrub what was already stored. Contact names never needed to leave the client in the first place — the server field was pure unused liability.
  • PositioningRewrote the landing page after judging it "too AI generated": cut four CTA blocks that duplicated the same checkout link with no new information, replaced emoji icons and a generated mockup graphic with real product screenshots and hand-drawn SVG icons, and broke up a repeated centred-icon-grid rhythm with an asymmetric two-column layout. Translated all new and changed copy into the site's other 8 languages by hand, catching a stale hero-copy string that had silently gone untranslated in all 8 along the way.

Case study: applied AI systems architecture

KasaFlow

AI Customer Workflow Engine · Python / FastAPI · OpenAI Responses API

Self-directed · hardened

A modular AI workflow engine that combines FastAPI, Python, and OpenAI's Responses API to process customer requests using structured LLM outputs and deterministic business tools, not a single script wired to one model call.

  • V1Deterministic, rule-based routing. Predictable, but brittle against real customer phrasing.
  • MigrationSwapped intent recognition for GPT-4.1-mini via the OpenAI Responses API, engineering prompts that reliably return structured JSON instead of conversational text.
  • OrchestrationAPI, LLM, routing logic, and business services split into independent modules, so the contract stays stable no matter what's doing the work underneath.
  • Tool layerBuilt a Tool Registry and generic Tool Executor that dynamically dispatch AI-selected tools (pricing, delivery, quote generation, product recommendation) based on structured LLM output, backed by external JSON datasets kept separate from application logic.
  • RoutingEvolved from deterministic rule-based routing to LLM-driven tool selection as the system matured.
  • HardeningRetries with backoff on transient LLM failures, defensive JSON parsing, Pydantic request validation, and structured logging in place of scattered print statements.
  • Testing798-passing / 29-gated test suite spanning unit, integration, and prompt regression tests, kept fast and free by gating real-API regression tests behind an opt-in flag.
  • VoiceIntegrated Khaya AI's ASR and TTS for Twi voice notes, the way most customers actually reach the pilot business. Confirmed the real API host, auth header, and request/response shapes against live calls first, not documentation alone, then rewrote the wrapper against what was actually true.
  • CommerceSynced the pilot business's real WooCommerce catalogue and wired the WhatsApp Cloud API in, extending the engine from a text-in/JSON-out service into a customer-facing WhatsApp assistant, image replies included when a matched product has a photo.
  • IncidentA new semantic-search fallback made a genuine, unmocked network call to the embeddings API, which the existing test suite's own stated design principle, "no server, no network, no AI", never expected, and which failed hard in CI's sandboxed environment. Root-caused by reading what the existing tests actually guaranteed rather than the error output alone, then fixed with a try/except boundary that is also the correct production behaviour, not just a test workaround: a real customer's request shouldn't crash because OpenAI had a bad moment. Confirmed fixed by watching CI go from red to green on the fix commit, not by trusting the fix locally.
  • Action layerEvery tool up to this point was read-only. Added the first one that writes: propose_order() prices an order deterministically and never touches WooCommerce; confirm_order() is the only function that does, and it only ever acts on whatever propose_order() already priced for that session, never on arguments of its own — a second, session-scoped confirmation gate on top of the existing LLM-decides/code-executes split, added specifically because this is the first tool with a real, hard-to-undo side effect. Orders land as WooCommerce's on-hold status; payment collection is a deliberately separate, not-yet-built problem.
  • IdempotencyWooCommerce's REST API has no idempotency-key support. Considered a reconciliation job and a WooCommerce-side plugin, rejected both as heavier than the actual failure mode warranted, and shipped the narrower fix: on a timed-out order-create, look the order up by a token embedded in its own metadata before deciding whether to retry, instead of risking a duplicate. Event-driven WooCommerce webhooks noted as the more correct long-term replacement, deferred until payment confirmation is built.
  • Live verificationProvisioned real WhatsApp Cloud API credentials and proved the full round trip against a live phone, not a mock: a real inbound message routed through the LLM, fell back to semantic search on a non-exact product match, priced it against the live WooCommerce catalogue, and came back as a real image-plus-price reply on WhatsApp. Also found and worked around a real platform constraint along the way -- Meta withholds real inbound webhook delivery entirely from an unpublished app, confirmed by direct A/B test rather than assumed from docs, so a webhook-shaped payload gets POSTed straight to the local endpoint for development instead of waiting on business verification.
  • Conversational layerLive testing surfaced a real gap: pure social messages ("oh wow", "sigh") were being forced through business tools that had nothing to do with them. Added an eighth LLM outcome, converse, scoped so the router short-circuits it before it can touch order, product, or memory state -- confirmed with dedicated isolation tests that a stray aside can't silently clear a pending lookup or overwrite an in-progress order.
  • State trackingClosed a second gap from the same live run: the assistant had no memory of *why* its own last action had just failed, so a customer asking "why?" got a generic non-answer. Added pending_intent (an unresolved product lookup) and last_action_outcome (a genuine, unrecoverable business-action failure, deliberately distinct from "still gathering info") to session memory, each cleared by its own stricter success check so a failure can't be wiped out by the very call that just recorded it.
  • Product-matching bugRoot-caused a live wrong-product substitution against the real catalogue: karat and weight suffixes like "14k" and "16g" were stripping to bare letter fragments ("k", "g") that substring-matched almost any product name, silently outranking the correct item in keyword-overlap scoring. Fixed with a minimum-token-length filter, confirmed against the actual 3,918-product catalogue -- the wrong product's score dropped from 7 to 4, the correct product's held at 5 -- not just against synthetic test fixtures.
  • Order correctionsFixed the in-progress-order flow silently keeping a stale field (e.g. "Accra") after a customer explicitly corrected it mid-conversation ("sorry, Kumasi not Accra"). The prompt now carries an explicit correction exception rather than only ever filling in blanks.
  • Live orderThe missing write-scoped WooCommerce credential flagged as the open item in the previous update was provisioned. A real order landed in the live store on the first attempt, confirming the root cause diagnosed earlier was the actual, and only, blocker.
  • CancellationA live customer transcript surfaced two gaps at once: a delivery address naming one city while the chosen delivery option named another, and no way to cancel an order once placed. Added a conservative, one-directional address/option mismatch check that only ever routes an ambiguous case to manual staff confirmation, never asserts a wrong delivery arrangement outright; added a full cancel_order tool reusing the existing session-scoped confirmation infrastructure, preferring an explicit order number with a last-confirmed-order fallback; and softened the customer-facing "confirmed" wording to "placed", since nothing is actually settled until a human arranges payment and delivery. Diagnosed, fixed, and covered by 30 new tests the same day.
  • Ambiguity guardA live evaluator run surfaced a real gap: a bare reference back to a just-shown product list ("the ring", "that one") could get silently resolved to the wrong item, or, in the safer but still poor case, correctly decline to guess and fall through to a generic "couldn't find that" reply that threw away the fact a list had just been shown at all. Built a deterministic, post-hoc guard that steps in only when a genuine multi-item ambiguity exists, with clarification wording that scales to how many items are actually ambiguous, plus a stash that carries other details already stated in the same breath (a karat, a quantity) through to the turn the customer actually answers. Fixing it surfaced a second, separate bug: the stashed field was being forwarded to whatever tool the follow-up resolved to regardless of whether that tool's own function signature accepted it, an order quantity reaching a plain price-lookup call that has no such parameter at all. Both fixed and confirmed against the full test suite the same day, with the live evaluator scenario passing 6/6 on repeat runs afterwards.
